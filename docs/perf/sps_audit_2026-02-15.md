# SPS Performance Audit (2026-02-15)

This document consolidates the latest SPS/performance investigation across `docs/perf`, training runs, and end-to-end
training code paths.

## Scope

- Hardware tested:
  - `metta4` (single RTX 4090)
  - `relh-sandbox-1` (4 GPUs via `run.sh`)
- Recipe/workload: `cogsguard.train`
- Goal: identify meaningful SPS wins without violating trajectory/replay correctness.

## Executive Summary

1. The dominant SPS costs in measured runs are `_rollout.inference` and `_train`, not env wait.
2. Increasing worker budget reduced `_rollout.env_wait` but made `_rollout.inference` slower, yielding worse net SPS.
3. `sync_traj=false` is currently not viable in this pipeline due to replay invariants (`Ghost progression detected`).
4. The best next optimization target should be inference/train path efficiency that preserves current trajectory
   semantics, with priority on multi-slice-relevant improvements (not single-slice-only shortcuts).

## Correctness Findings (Trajectory/Replay)

`sync_traj=false` on `relh-sandbox-1` repeatedly failed with:

`RuntimeError: Ghost progression detected: store() called for agents whose replay segments are already full.`

Relevant invariant enforcement:

- `metta/rl/training/experience.py:252`
- `metta/rl/training/experience.py:264`

The replay contract is strict row ownership and no silent dropping/reassignment; any optimization must preserve this.

## What We Learned From Failed/Weak Ideas

1. Worker-budget expansion alone is not enough:
   - It reduced env wait but increased inference share and reduced steady-state SPS.
2. Async env waiting with `async_factor=2` is expected and can be healthy overlap behavior.
3. For this pipeline, correctness guardrails around replay/trajectory consumption are active and should remain active.

## Prioritized Optimization Backlog (Multi-Slice Aware)

1. **Trajectory isolation data-movement reduction (high priority, multi-slice relevant)**  
   Reduce clone/cat/split/writeback churn in rollout and training while keeping slice semantics unchanged.

2. **Inference path throughput improvements (high priority, multi-slice relevant)**  
   Since `_rollout.inference` is the largest bucket, optimize policy-forward batching and per-step overhead around it.

3. **Training minibatch path efficiency (medium-high, multi-slice relevant)**  
   Reduce per-slice sampling/assembly overhead in `_train` loops.

4. **Backpressure design for async recv/send (medium, correctness-first)**  
   If revisiting `sync_traj=false`, it must include explicit backpressure so done rows are not advanced.

5. **Env wait tuning (lower priority after above)**  
   `_rollout.env_wait` is smaller than inference/train in these runs; optimize only after core hot buckets.

### Pattern from this history

1. Many micro-optimizations are fragile across hardware topology.
2. Vecenv scheduling changes can produce large multi gains but often regress single-GPU.
3. Mixed-precision/checkpointing style changes can hurt multi throughput significantly when they increase
   synchronization pressure.
4. Several robust wins are already merged, so remaining easy wins are narrower.

## Backlog Write-Up (Post-Historical-Audit)

Given the above history, the most likely meaningful next SPS gain is to optimize shared training hot paths that:

- are topology-agnostic,
- apply to multi-slice runs,
- and reduce the two largest measured buckets (`_rollout.inference` and `_train`).

Priority order:

1. **Trajectory-isolation execution path simplification (multi-slice safe)**  
   Target clone/cat/split/writeback overhead in `trajectory_isolation.py` and the corresponding calls in `core.py`,
   while preserving row ownership and slice correctness.

2. **Training-phase slice minibatch assembly reduction**  
   Reduce repeated per-minibatch per-slice assembly work (`sample_slice_minibatch`, concat/split churn) in `core.py:705`
   onward and `trajectory_isolation.py:442` onward.

3. **Policy-forward overhead trims around rollout orchestration**  
   Keep the policy network architecture fixed; optimize orchestration cost around policy forward calls so gains apply to
   both single and multi.

4. **Topology-specific toggles only for clearly divergent vecenv ideas**  
   Revisit high-divergence vecenv candidates (`#6936`, `#6938`) only behind explicit topology gates and only after
   trajectory/replay invariants are guaranteed by design.

## Why Single-Slice Fast Path Is Deprioritized

A single-slice fast path could still help default/sweep-style runs, but it does not match frequent multi-slice
production workloads. The near-term optimization should therefore target shared multi-slice paths first.

## H25 Simplification: Direct Rollout Writeback Fast Path (2026-02-16 Night)

Change:

- commit `4918dd43aa` (carried in branch tip `6fbb99cecf`)
- `TrajectoryIsolator.writeback_rollout_tds()` caches a per-slice mode:
  - `direct`: `rollout_td[mask] = slice_td` when keys/dtypes/shapes match
  - `pad`: fallback to existing `_pad_slice_td_like()` when mismatch or assignment fails

Why this is plausible:

- writeback currently rebuilds new TensorDicts and clones tensors in `_pad_slice_td_like()` for every slice every step
  where outputs exist, even in the common case where shapes are already aligned.
- direct assignment avoids that clone/pad churn while preserving exact output semantics when compatible.
